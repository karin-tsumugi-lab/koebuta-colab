# シナリオ化プロンプトv0.3 外部レビューへの対応

2026-11-16（日本時間）。対象はPR #7のコミット `3e198583` を収録したレビュー用ZIP。ユーザー提供のGeminiの初見レビューとMuseの詳細Markdownレビューを読み、公開リポジトリの実装・既存合意に照合した。

Muse側は独自改変を含む継続利用環境、Gemini側は初見の利用という前提を考慮する。利用経験は運用上の論点として扱い、実装条件は公開版で再確認する。外部レビューの「文書に矛盾なし」は、アプリ実装や演出品質の実証とは区別する。

## 採否と最終的な変更

| 指摘 | 判断・対応 |
| --- | --- |
| Muse 中1：見出し結合と改変許可の境界 | 採用。連続する原稿範囲の文字・空白・改行・順序を保った結合は許可不要。行の区切り削除や導入文への言い換えとは区別。結合自体は義務にせず、演出判断を残す |
| Muse 中2／Gemini：照合警告の重複 | 採用。02本文は許可の記録・原稿照合・検証を隠さない制約だけに圧縮。アプリごとの詳細はエディタ案内へ集約し、01・03B・エージェント手順は必要な要約・参照にする |
| Muse 軽微1：区切りにも間を指定可能と明示 | 採用。02に区切りの `pause_after_ms` を追記 |
| Muse 軽微2：複数人の地の文のname | 採用。02に `name: "地の文"` を追記 |
| Muse 軽微3：区切りのemotion | 採用。01の表にも区切りは `neutral` を付けると明記 |
| Muse 軽微4：見出し類の外縁 | 保守的に明確化。目次・奥付・刊行情報・ページの柱・定型前後文へ許可を自動拡張しない。改変が必要なら対象と操作を別途確認し、無断で省略しない |
| Gemini：一人朗読とnarratorEmotion | 採用。既存のエージェント手順の設定例・説明を維持し、02補足・03Bにも生成設定の注意を追加。emotion反映が無効でも `acting_description` まで消えるわけではないので、「すべてneutralになる」とは説明しない |
| Gemini：CLIのseparatorのspeaker_id | 公開CLIの実入口で再現し採用。登録済みIDに加え空白だけでない `text` も必要。空行へ記号を創作する対応は禁止し、直前発話の `pause_after_ms` を使う方法を案内。CLIコード・交換形式の構造は変更しない |
| Gemini：任意の演出メモ出力 | 簡潔な補足として採用。要求された場合はJSON外へ提示する。指定欄を増やしたり、既定のJSONのみ出力を変更したりしない |
| Gemini：位置タグ併用時のneutral推奨 | 保留。根拠として挙げられた別ガイドラインは今回の資料に含まれず、併用の不安定性を公開版で確認できていない。一律neutralへ寄せる新規則は追加せず、試聴による確認方針を維持 |
| Muse：落ち着いた語りを出発点の例にする | 今回は採用しない。作品と声からAIが全体演出を判断する方針を維持し、固定の語りの既定値を導入しない |
| Muse：固定ケースを保持 | 採用。[5条件と境界ケース](SCENARIO_PROMPT_REVIEW_CASES.md)を文書化。LLM出力の分割位置・感情の完全一致は求めず、原文・許可・構造の適合と演出判断を分ける |
| Muse：02冒頭の「最小」の表現 | 採用。単独で使える構造・制約を含む、と修正 |

Museの机上評価で短い台詞の単独維持を「正解」とした箇所は、必須規則として採用しない。一人朗読では同じ朗読者の地の文・台詞を自然に結合でき、分割の違いだけを不適合としない。

## 検証とレビューの範囲

この追加修正はMarkdownのみ。Notebook・CLI・HTML・スキーマ・テストコードと、過去の検証記録は変更しない。

修正前の公開CLI実入口で、区切りの話者省略は終了1（未登録話者）、登録済み話者＋原稿の区切り文字は終了0、話者を付けても空の `text` は終了1を再現した。よってspeaker_idだけを補足する対応では不足すると判断した。

修正後は、ローカルリンク、JSON例、emotion34種類・位置10タグ・除外4タグ、原文不変の見出し結合、区切りの入力条件、生成設定による語り手の感情反映、差分の変更対象を確認する。実行コマンドと結果は確認完了後、次節へ記録する。固定ケースは受け入れ条件であり、独立したLLMの新しい生成結果やTTS品質改善を実証したものではない。

## 実行結果

Windows / Python 3.14.3。検証用JSON・設定は一時ディレクトリへ作り、CLI実入口を次の形で実行した。ネットワーク・GPUは使用しない。

```text
python cli/irodori_generate.py --scenario <Tempのscenario.json> --settings <Tempのsettings.json> --session review --job review --out <Tempの未作成出力先> --dry-run --no-usage
```

| ケース・コマンド | 結果 |
| --- | --- |
| 改行付き見出しと本文 | 終了0。見出しの改行を保持し、入力JSONは不変。ただし3行の見出しはCLI内部で3生成片へ分かれ、本文と計4要求となった。原文不変の結合だけでは短文生成回避を保証しないことを02・CLI案内等へ追記 |
| 区切りのspeaker_id省略 | 終了1、未登録話者エラー |
| 区切りに登録済みspeaker_id＋原稿の記号＋900ms | 終了0。区切り自体は音声要求にならず、直前の発話へ900msを反映 |
| 区切りに登録済みspeaker_id＋空text | 終了1、空でないtextが必要というエラー |
| 空行だけの原稿、区切りなし、直前発話へ900ms | 終了0。原稿・空行を保持し、記号や追加の音声要求を作らず900msを反映 |
| 語り手のjoy、emotion=true、narratorEmotion=false/true | 両方終了0。falseでは感情タグなし、trueでは喜びタグを先頭へ付加。acting=trueによる話者・発話の演技説明はどちらもCaptionへ残った |
| Markdownローカルリンク | 変更・追加文書10件の46リンクに欠落なし |
| JSON例・フェンス | jsonフェンスの4例と02のtextフェンス内の標準例をparse、フェンス対応も正常 |
| 感情・絵文字 | 02の候補が公式emotion ID34種類と完全一致。位置10タグ・除外4タグのUnicode文字列を保持。発話全体の感情はIDで指定するため、全感情の絵文字そのものを02へ重複列挙する必要はない |
| `git -c core.autocrlf=false diff --check` | 終了0。変更はMarkdownのみ |

すべてのCLI検証で入力JSONのバイト列は不変。メイン担当は差分・規則の相互整合をレビューし、テスト担当の実測と照合した。コード変更がないため既存30件の回帰試験は今回は再実行していない。以前の成功結果と今回のdry-runを区別する。

実GPU・音声生成・試聴、実ブラウザー操作、外部LLMの再実行は未実施。机上の5条件は固定したが、演出品質の改善や外部モデルの出力傾向を新たに実証したものではない。
