# Koebuta v3 シナリオ制作・朗読出力 詳細仕様

2026年11月20日　実装仕様

## 1. 目的と適用範囲

一つの `scenario.json` を、AIによるシナリオ制作、Inspectorでの確認、CLIでの朗読生成、生成後の音声編集に使う。ユーザーは発話IDを手掛かりに、原稿、読み、編集指示、個別WAVを相互に照合できる。

本書は既存のシナリオ交換形式v1への追加仕様である。話者、感情、休止などの基礎仕様は[現行仕様書](../notebook/01_SPEC_SHEET.md)による。v3はKoebutaの版名であり、以下のJSON例では `schema_version: 1` を使う。ルビの区別、自由記述の編集指示、発話IDと個別WAVの対応を設計の前提とする。追加項目名、ルビの位置表現、編集時の引き継ぎ方法を以下に定める。

v3の正式な生成経路はCLIの `irodori_generate.py` とする。Notebookは旧資料として扱う。

## 2. シナリオ生成前の対話

1. **原稿を把握する。** AIは受領範囲を確認し、題名・著者・見出し・本文・注記・底本情報、章や場面の境界、語り手・話者・引用の関係、作品の調子と演技の変化、作者ルビ・固有名・読み分け・歴史的表記を読む。長編では、話者やルビを章をまたいで確認するため時間を要する旨を着手時に短く伝えて作業を始める。抜粋では読めた範囲を明示する。
2. **作品に必要な選択を一度に提示する。** 原稿理解を一、二文で示し、推奨案と「おまかせ」で進められる選択肢を提示する。対象は、朗読範囲、声の割り当て、読みや演出の方針、許可が必要な見出しの言い換えなど、出来上がる朗読を変える事項とする。既に依頼で決まった項目は質問から外す。個々のルビ候補や発話分割を順番に承認させない。
3. **回答を受けて生成する。** 通常の方針確認は一往復とし、判断事項がすべて指定済みならそのまま進める。「おまかせ」は提示した推奨案の採用として扱う。原稿欠落や相反する明示指示など、制作を続けられない場合だけ追加確認する。本文と、提供された原文 `source` を保持し、読みの調整は読み上げ側に反映する。

## 3. ルビの由来と採用

シナリオ作成時に読み上げ側のルビを青空文庫形式 `｜親文字《読み》` に揃える。範囲は縦棒から `《` の直前までとする。カクヨムの傍点はルビの対象外である。改ページ・字下げ・見出しなど既知の青空文庫の組版注記は原文に保持し、合成入力から除く。なろう・カクヨム・pixivなどから作る場合は `text`・`source` に原文を保持し、元形式を `text_format` で指定し、変換した全文を `tts_text` に置く。既存の別形式の発話はその発話に追加ルビ欄を設けるまでは既存の処理で読める。変換後に作者ルビが欠落していても、対象箇所が一意なら原文の読みを合成入力に復元する。変換後に異なる読みが指定されていれば、両方の読みを示して確認を求める。

| 由来 | 制作時の扱い | 生成時の扱い |
|---|---|---|
| 原文にあるルビ | 作者指定の読みを保持する | 必ず採用する |
| 原文ルビを同じ表記・同じ読みに補ったもの | 文脈から同じ読みと確認できた出現箇所へ補う。作者ルビと同じ表示でよい | 必ず採用する |
| AI・編集者が追加したルビ | 原文に指定のない漢字、旧仮名遣い、送り仮名や訓読み表記の揺れなどに補ったルビには、すべて追加由来を記録する | 手動確定を優先し、自動判定を選んだ箇所だけをスコア判定する |

同じ字面でも、駅名「放出」と動詞「放出」の読みは個々の文脈で決める。Inspectorでは追加ルビに🔖などの表示を添える。印は表示のために描画し、原文・TTS入力・感情タグ列には書き込まない。読みを採用した後も追加由来は残す。

**データ表現。** 各発話に任意の配列 `koebuta_added_ruby` を置く。各要素は、その発話の `text` 中の対象位置、表記、読み、採用状態を持つ。位置はUnicodeコードポイント単位、先頭0、終端を含まない区間とする。位置と表記を併記し、同じ語の二度目にも一意に指定できるようにする。

| 採用状態 | 意味 |
|---|---|
| `auto` | v3の自動選択で仮名化か元表記かを決める |
| `kana` | 人が読みを確定。指定の仮名を使う |
| `surface` | 人が元表記を確定。表記を維持する |

v3の生成計画には、確定済みの読みを反映した全文を表示する。遠隔で判定する自動候補は `--dry-run` の `ruby_pending` に発話ID・対象・候補の読みを出す。判定待ちの箇所は元表記を表示し、採用結果は未確定とする。既に手で編集された `tts_text` がある場合は、その全文を保持して対象箇所を照合する。位置を一意に対応付けられないときは要確認に戻し、全文を機械的に組み直さない。必須ルビと追加候補が同じ箇所に重なるときは必須ルビを優先する。範囲外、表記不一致、追加候補同士の重複は該当箇所を示す。

**閾値の扱い。** 試作の `auto_select` 既定値は1トークンが0.65、複数が0.8327で、スコアが閾値以下なら仮名化する。0.67および0.90は比較した候補値にとどめる。閾値検証は今回で終了し、v3でもこの値を出発点とする。作者指定や手動確定がスコアで取り消されることのない生成経路を設ける。由来のない既存JSONは従来の設定で再生できるようにし、開いただけで過去の読みを再分類しない。

## 4. 自由記述の編集指示

各発話に任意の文字列配列 `notes` を置く。推奨書式は「[用途] 指示文」。独自タグ、タグのない日本語、複数行の指示を保持する。挿入位置は「この発話の直後」「次の発話中」などと書ける。複数発話にわたる指示では、必要に応じて本文中に終端の発話IDを書ける。

効果音はユーザーが別途用意する外部素材である。素材名・ファイルパスが未定でもシナリオを作成・保存・朗読できる。指示の解釈、発話間への挿入、混音、既存休止との調整はユーザーに一任する。Koebutaは記述を表示・保存し、TTSには渡さない。素材台帳や別の指示ファイルは不要である。再試聴、録り直し、チャプター候補なども同じ欄を使える。

### シナリオ例

```json
{
  "schema_version": 1,
  "speakers": {
    "narrator": {"name": "語り手", "kind": "narrator"}
  },
  "segments": [
    {
      "id": "t0001",
      "speaker_id": "narrator",
      "text": "井戸から冷い水をくんだ。",
      "emotion": "neutral",
      "koebuta_added_ruby": [
        {"start": 4, "end": 6, "surface": "冷い", "reading": "つめたい", "selection": "kana"}
      ],
      "notes": ["[効果音] この発話の直後に桶を置く音。素材は後で選ぶ。"]
    },
    {
      "id": "t0002",
      "speaker_id": "narrator",
      "text": "しばらくして、水面が静かになった。",
      "emotion": "neutral",
      "notes": ["[編集] この発話にだけ小さく水音を重ねる"]
    }
  ]
}
```

v3対応生成器での第1発話の期待入力は「井戸からつめたい水をくんだ。」。第2発話は本文どおり。個別WAVには朗読音声を収め、効果音文や🔖を含めない。旧生成器は追加フィールドを解釈しないため、手動採用済みの読みも旧版で使う場合は、互換用の書き出し時に解決済みの読み上げ全文を `tts_text` に反映する。CLIで `--export-compatible 出力.json` を指定する。自動候補は元表記で書き出すため、旧版へ渡す前に必要な読みを手動確定する。

## 5. 発話ID・個別WAV・編集時の整合性

- 発話IDは作品内で一意とし、朗読順は `segments` の配列順とする。新規作成時は `t0001` からの4桁ゼロ埋めを推奨する。長編分割では章接頭辞も使える。既存の `T1` や `t001` は保持する。挿入や並べ替えで後続の発話を一括改番しない。
- CLIでは、利用者に渡す個別WAVのファイル名は標準文字で構成した発話IDから始める。後続にはテイク識別子や話者名などを付けられる。例は `t0001_narrator.wav`。旧データから出力した親発話WAVの名前が大文字・小文字を区別しない環境で重なる場合は、IDの後ろに `__1` などを付ける。任意の入力IDをパスとして扱わず、安全な名前への変換で衝突した場合は両者を識別できる形にする。
- v3では一発話を一つの生成単位とし、長い文章は別発話にする。間に発話を差し込みやすい `t0010`、`t0020` といった10刻みの採番も使える。追加ルビ欄のある発話では旧TTS片を受理しない。
- 本文編集ではルビ範囲と対象表記を再照合する。発話分割では、出現箇所を特定できるルビは該当側に引き継ぐ。自由記述の指示は意味を推測して複製・移動せず、元の発話IDと指示を示して編集者が配置を確認できるようにする。結合・削除でも未解決の指示が見えなくならないようにする。
- 採用済み音声の再利用は、実際の読み上げ文、声、モデル、演技条件など合成に関わる条件で判定する。メモだけの変更では朗読の再生成を要求しない。作品の変更記録と音声の再利用判定は個別に扱う。休止の変更は既存の結合処理に反映する。

## 6. 実装前に確認済みの範囲

試作CLIでは最上位と発話内の独自項目が転送後も残り、生成要求・休止・模擬合成に渡した入力が一致した。一方、シナリオ全体を含む計画署名は変わった。Notebook v2では計画の一致とJSON再出力時の独自項目保持を確認した。Inspectorでは診断と通常のJSON保存を確認した。分割・結合・Drive復元までの完全な互換性は未検証である。

本文に書いた🔖は試作CLIの `none`、`original`、`partial_kana` で合成入力に残った。独立した `segment_type: "sfx"` は既存経路で未知種別として扱われる。これらの観測を、発話内の独自項目を使う根拠とする。追加ルビの採用規則やWAV命名の統一はv3の実装対象である。

## 7. 受け入れ条件

| ケース | 合格とする観測 |
|---|---|
| 長編原稿と短編の「おまかせ」 | 長編は把握に時間がかかる旨を先に伝える。必要な選択を一度に提示し、回答後に生成へ進む。条件が揃った短編では重ねて尋ねない |
| 作者ルビと追加ルビが混在 | 作者指定と同じ読みに補った箇所は必ず指定読みになる。追加候補だけが自動判定対象となり、手動確定と由来は保存・再読込後も保持される |
| 同一表記が二度ある発話 | 一方の読みだけを変更でき、他方の読みと原稿を保持する。対象がずれれば要確認を表示する |
| 水音メモの追記と修正 | 同じ発話IDでメモを往復保存できる。変更前後でTTS要求・休止・個別音声の合成条件が一致し、素材未指定でも生成計画が通る |
| 発話の分割・結合・挿入 | 維持すべきIDは保持し、追加ルビ・メモの引き継ぎ先または未解決状態を確認できる |
| CLIのWAV書き出し | 展開したファイル名の先頭から発話IDを照合できる。Windowsのように大文字と小文字を区別しない環境でも、IDの異なる発話が同じファイルを上書きしない |
| 旧作品と互換用書き出し | 旧作品を従来条件で開いた際のTTS入力が一致する。v3で確定した読みを互換出力した場合は、旧版の生成計画でもその読みを確認できる |

本書の受け入れ条件は今後の実装で検証する。`selection: "auto"` はCLIの既定操作で自動判定を有効にする。ルビの位置がずれた場合はInspectorの診断と生成前のエラーに対象を表示する。

既存シナリオとの互換性のため、v3ルビ処理は発話単位で有効になる。新規v3シナリオでは各発話に `koebuta_added_ruby` を置き、追加ルビがなければ空配列とする。

### 仕様と観測の対応

- 作者ルビ、手動採用ルビ、同一表記の自動候補を含むテストでは、自動候補の一箇所だけがスコア判定へ渡り、残りは指定読みになった。
- 効果音の指示だけを書き換えた前後で、CLIの合成要求が一致した。
- 発話を分割すると対象語のある側に追加ルビが移り、位置が新しい発話の先頭を基準に更新された。元の発話IDに指示が残り、配置確認の通知を出した。
- 旧版向け書き出しでは確定済みの読みが読み上げ全文に反映され、編集指示が保持された。
- 実GPUでの通し生成と、実原稿を使った制作前の対話評価は未実施。

- なろうの括弧ルビ・カクヨムの傍点・pixivのルビを含む原文は保持され、青空文庫形式の読み上げ文から生成計画を作成できた。旧形式の別発話の読みも従来どおりだった。
- 旧TTS片とv3追加ルビの併用をCLIが診断すること、旧データの親発話WAVでは T1・t1・t1__1・CON が異なるWindows対応パスになることを確認した。

- 既知の青空文庫注記を原文に残し、合成入力から除いた。追加ルビの位置は注記を含む原文基準で照合できた。遠隔判定を予定するdry-runは作者指定と手動確定を反映し、自動候補を `ruby_pending` に表示した。

- なろう・カクヨム・pixiv・青空文庫の各原文で、作業文から作者ルビが落ちたときは読みを復元し、別のルビに変わったときは生成前に両方の読みを表示して止まることを確認した。
