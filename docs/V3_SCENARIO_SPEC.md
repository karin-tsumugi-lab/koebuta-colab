# Koebuta v3 シナリオ制作・朗読出力 詳細仕様

## 1. 目的と適用範囲

一つの `scenario.json` を、AIによるシナリオ制作、Scenario Inspector（HTMLエディタ）での確認、CLI（`cli/irodori_generate.py`）での朗読生成、生成後の音声編集に共通して使用する。利用者は発話IDを手掛かりに、原稿、読み、自由記述の編集指示、個別WAVを相互に照合できる。

本書はシナリオ交換形式（`schema_version: 1`）におけるv3仕様を定める。話者、感情、休止などの基礎構造は [シナリオJSON仕様書](../prompts/01_SPEC_SHEET.md) による。

---

## 2. シナリオ生成前の対話原則

1. **原稿を把握する。** AIは受領範囲を確認し、題名・著者・見出し・本文・注記・底本情報、章や場面の境界、語り手・話者・引用の関係、作品の調子と演技の変化、作者ルビ・固有名・読み分け・歴史的表記を通読する。長編では着手時に時間を要する旨を短く伝えて作業を始める。
2. **作品に必要な選択を一度に提示する。** 原稿理解を一、二文で示し、推奨案と「おまかせ」で進められる選択肢をまとめて提示する。対象は、朗読形式・範囲、声の割り当て、読みや演出の方針、許可が必要な見出しの言い換えなど、出来上がる朗読を変える事項とする。既に依頼で決まった項目は質問から外す。個々のルビ候補や発話分割を順番に承認させない。
3. **回答を受けて生成する。** 通常の方針確認は一往復とし、判断事項がすべて指定済みならそのまま進める。「おまかせ」は提示した推奨案の採用として扱う。本文と提供された原文 `source` を保持し、読みの調整は読み上げ側（`tts_text` / `koebuta_added_ruby`）に反映する。

---

## 3. ルビの由来と採用規則

シナリオ作成時に読み上げ側のインラインルビは青空文庫形式 `｜親文字《読み》` に揃える。範囲は縦棒から `《` の直前までとする。カクヨムの傍点（`《《…》》`）はルビの対象外である。改ページ・字下げ・見出しなど既知の青空文庫の組版注記は原文 `text` に保持し、合成入力から自動的に除く。

なろう・カクヨム・pixivなどから作る場合は `text`・`source` に原文を保持し、元形式を `text_format` で指定し、青空文庫形式に変換した全文を `tts_text` に置く。変換後に作者ルビが欠落していても、対象箇所が一意なら原文の読みを合成入力に復元する。変換後に原文と異なる読みが指定されていれば、両方の読みを示してエラーとし確認を求める。

| 由来 | 制作時の扱い | 生成時の扱い |
|---|---|---|
| **原文にあるルビ** | 作者指定の読みを保持する | 必ず採用する |
| **原文ルビを同じ表記・同じ読みに補ったもの** | 文脈から同じ読みと確認できた出現箇所へ `tts_text` 上で青空文庫形式にて補う | 必ず採用する |
| **AI・編集者が追加したルビ** | 原文に指定のない漢字、旧仮名遣い、送り仮名や訓読み表記の揺れなどに補ったルビには、すべて追加由来（`koebuta_added_ruby`）を記録する | 手動確定（`kana` / `surface`）を優先し、自動判定（`auto`）を選んだ箇所だけをスコア判定する |

同じ字面でも、駅名「放出」と動詞「放出」の読みは個々の文脈で決める。Scenario Inspectorでは追加ルビに `🔖` を添えて表示するが、印は表示用に描画するものであり、原文・TTS入力・感情タグ列には書き込まない。

### データ表現（`koebuta_added_ruby`）

各発話に任意の配列 `koebuta_added_ruby` を置く（出力トークン節約のため、追加ルビがない発話ではキー自体を省略してよい。空配列 `[]` も許容する）。各要素は、その発話の `text` 中の対象位置、表記、読み、採用状態を持つ。位置はUnicodeコードポイント単位、先頭 `0`、終端を含まない区間 `[start, end)` とする。位置と表記を併記し、同じ語が同一発話内に二度出現しても一意に指定できるようにする。

| 採用状態（`selection`） | 意味 |
|---|---|
| `auto` | v3の自動選択（`auto_select`）で仮名化か元表記かを決める |
| `kana` | 人が読みを確定。指定の仮名を使う |
| `surface` | 人が元表記を確定。表記を維持する |

- CLIの `--dry-run` では、作者ルビと手動確定済みの読みを反映した全文を `requests` に表示し、遠隔で判定する `auto` 候補は `ruby_pending` に発話ID・対象・候補の読みを表示する。
- 必須ルビ（作者ルビ）と追加ルビ候補が同じ箇所に重なるときは必須ルビを優先する。範囲外、表記不一致、追加候補同士の重複は生成前にエラーとして該当箇所を示す。
- **自動選択の閾値**: `auto_select` の既定閾値は1トークン語が `0.65`、複数トークン語が `0.8327` とし、テキストエンコーダ特徴量の類似度スコア（`cos_cond`）が閾値以下なら仮名化する。スコア判定は特徴量類似度と閾値に基づく機械判定であるため、文脈上の読み分けや確実に指定の読みで読ませたい語は手動確定（`kana` / `surface`）を優先する。作者指定や手動確定がスコア判定で取り消されることはない。

## 4. 自由記述の編集指示（`notes`）

各発話に任意の文字列配列 `notes` を置く。推奨書式は `"[用途] 指示文"`（独自タグ、タグのない日本語、複数行の指示も保持する）。挿入位置は「この発話の直後」「次の発話中」などと記述でき、複数発話にわたる指示では終端の発話IDを書ける。

効果音やBGMは利用者が別途用意する外部素材であり、素材名・ファイルパスが未定でもシナリオを作成・保存・朗読生成できる。Koebutaは `notes` を表示・往復保存し、TTSには渡さない。再試聴、録り直し、チャプター候補なども同じ欄を使える。

### シナリオ例

```json
{
  "schema_version": 1,
  "speakers": {
    "narrator": {"name": "語り手", "kind": "narrator"}
  },
  "segments": [
    {
      "id": "t0001",
      "speaker_id": "narrator",
      "text": "井戸から冷い水をくんだ。",
      "emotion": "neutral",
      "koebuta_added_ruby": [
        {"start": 4, "end": 6, "surface": "冷い", "reading": "つめたい", "selection": "kana"}
      ],
      "notes": ["[効果音] この発話の直後に桶を置く音。素材は後で選ぶ。"]
    },
    {
      "id": "t0002",
      "speaker_id": "narrator",
      "text": "しばらくして、水面が静かになった。",
      "emotion": "neutral",
      "koebuta_added_ruby": [],
      "notes": ["[編集] この発話にだけ小さく水音を重ねる"]
    }
  ]
}
```

第1発話の合成入力は「井戸からつめたい水をくんだ。」、第2発話は本文どおりとなる。個別WAVには朗読音声のみが収められる。旧版ツール向けに解決済みの読みを `tts_text` へ書き出す場合は、CLIで `--export-compatible 出力.json` を使用する。

## 5. 発話ID・個別WAV・編集時の整合性

- **発話IDと採番**: 発話IDは作品内で一意とし、朗読順は `segments` の配列順とする。新規作成時は `t0001` からの4桁ゼロ埋め、または間に発話を差し込みやすい `t0010`、`t0020` といった10刻みの採番を推奨する（長編分割では章接頭辞 `c01_t0010` 等も可）。既存のIDは保持し、挿入や並べ替えで後続の発話を一括改番しない。
- **1発話＝1生成単位とWAV命名**: v3では一発話を一つの生成単位とし、長い文章は別発話に分ける。個別WAVのファイル名は発話IDから始まる（例：`audio/t0001_<fingerprint>_<id>.wav`）。大文字・小文字を区別しない環境（Windows等）で旧データの親発話WAV名が重なる場合や予約名（`CON` 等）に当たる場合は、`__1` 等のサフィックスで衝突を回避する。
- **編集時の引き継ぎ**:
  - 本文編集ではルビ範囲と対象表記を再照合する。
  - 発話分割では、出現箇所を特定できる追加ルビは該当側の発話へ引き継ぎ、文字位置を新しい発話の先頭基準に更新する。自由記述の指示（`notes`）は元の発話ID側に残し、編集者に配置確認を促す。
  - `notes` だけの変更では合成要求（fingerprint）は変化せず、音声の再生成を要求しない。

## 6. 受け入れ条件

| ケース | 合格とする挙動 |
|---|---|
| 長編原稿と短編の「おまかせ」 | 長編は把握に時間がかかる旨を先に伝える。必要な選択を一度に提示し、回答後に生成へ進む。条件が揃った短編では重ねて尋ねない |
| 作者ルビと追加ルビの混在 | 作者ルビおよび同語へ補った箇所は必ず指定読みになる。追加ルビの `auto` 候補だけが自動判定対象となり、手動確定と由来は保存・再読込後も保持される |
| 同一表記が二度ある発話 | 文字位置（`start` / `end`）により一方の読みだけを変更でき、他方の読みと原稿を保持する。対象位置がずれれば要確認エラーを表示する |
| 編集指示（`notes`）の追記と修正 | 同じ発話IDでメモを往復保存でき、変更前後でTTS合成要求・休止・個別音声の合成条件が一致する |
| 発話の分割・結合 | 維持すべきIDを保持し、追加ルビの引き継ぎと位置更新、および `notes` の確認通知が行われる |
| CLIのWAV書き出し | 展開したファイル名の先頭から発話IDを照合でき、Windows等の大文字・小文字を区別しない環境でもファイルが上書き衝突しない |
| 互換用書き出し（`--export-compatible`） | 確定した読みが `tts_text` に反映され、`koebuta_added_ruby` を解釈しない旧環境でも同じ読みで再生できる |
