# Koebuta 朗読シナリオJSON仕様書

- 文書状態：v1交換形式／Koebuta Colab v1.00の実装基準
- 形式バージョン：`schema_version: 1`
- 対象：Koebutaのシナリオ交換形式。各構成の読み込み許容・任意拡張への対応は [互換性表](../docs/EDITOR_GUIDE.md) を参照。CLI v1.0.1の生成設定は別JSONです。
- 役割：シナリオJSONの**意味と基本構造**を定める。LLMへの依頼方法、画面操作、GPU実行条件は定めない。

## 1. 基本方針

1. **生成側には簡潔な形式を求める。** LLMにハッシュ計算、文字数計算、独自の厳密検証、全文の再走査を要求しない。不明な解釈は無理に確定させない。
2. **受け取り側は寛容に解釈する。** 未知の項目や任意項目の欠落・不正値は、可能な限り無視または既定値に置き換え、使用した代替処理を必要に応じて通知する。
3. **原文と話者の対応を黙って改変しない。** 本文の削除、補完、置換、順序変更、別の話者への割り当ては自動で行わない。
4. **読み込みと音声生成を分離する。** シナリオの一部に問題があっても編集用に保持してよい。ただし音声生成に必要な情報が確定しない発話は、解決するまで生成しない。
5. **作品の規模を形式で制限しない。** 話者数、発話数、本文文字数、JSON全体の容量に仕様共通の最大値を設けない。アプリケーションは実行環境に応じた制限を設けられる。

## 2. 標準のJSON構造

```json
{
  "schema_version": 1,
  "source": "雨が降っていた。\n「明日、来る？」",
  "speakers": {
    "narrator": {
      "name": "地の文",
      "kind": "narrator",
      "voice_caption": "落ち着いた明瞭な声",
      "acting_description": "ゆったりとした語り口"
    },
    "aoi": {
      "name": "葵",
      "kind": "character",
      "bio": "原稿から読み取れる人物像"
    }
  },
  "segments": [
    {
      "id": "t001",
      "speaker_id": "narrator",
      "text": "雨が降っていた。",
      "emotion": "neutral"
    },
    {
      "id": "t002",
      "speaker_id": "aoi",
      "text": "「明日、来る？」",
      "emotion": "anxiety",
      "acting_description": "少しためらいながら"
    }
  ]
}
```

標準の出力では、トップレベルはJSONオブジェクトとし、`schema_version`、`speakers`、`segments` を含める。`source` は任意。出力に使用しない任意フィールドは省略してよい。従来のv1形式との互換性を保つため、話者の `name` と `kind`、発話の `emotion` は標準出力では必須のままにする。**標準出力形式と、受け取り側の救済的な読み込み許容範囲は同一ではない。**

### 2.1 トップレベル

| キー | 標準出力 | 意味 |
|---|---|---|
| `schema_version` | 必須 | 形式バージョン。現行は整数 `1` |
| `source` | 任意 | 入力原稿の全文。含める場合は空白・改行・ルビ・記号を含めて原文のまま保持 |
| `speakers` | 必須 | 話者IDをキーとするオブジェクト |
| `segments` | 必須 | 原稿の順に並んだ台本項目の配列 |

`source` を省略してもよい。長い原稿では重複出力を避けるため省略して構わない。受け取り側は `segments` を連結した文字列を「元の原稿全文」と称して `source` に補完してはならない。完全性を検査するには、信頼できる原稿の別途提供が必要な場合がある。

### 2.2 `speakers`（話者一覧）

| キー | 標準出力 | 意味 |
|---|---|---|
| `name` | 必須 | 画面に表示する話者名。地の文では「地の文」 |
| `kind` | 必須 | `narrator`（地の文）または `character`（登場人物） |
| `bio` | 任意 | 人物像。根拠のない設定を断定しない |
| `voice_caption` | 任意 | 声の特徴。声の試作に用いる説明 |
| `acting_description` | 任意 | 普段の話し方 |
| `age` | 任意 | `young_adult` / `adult` / `elderly` |
| `gender` | 任意 | `feminine` / `masculine` |
| `pitch` | 任意 | `high` / `mid` / `low` |
| `timbre` | 任意 | `clear` / `warm` / `soft` / `husky` / `bright` / `resonant` |
| `habitual_style` | 任意 | `gentle` / `measured` / `brisk` / `formal` / `casual` / `calm` |

- 話者IDは空でない文字列とし、標準出力では英数字・`_`・`-` を用いる。長さの固定上限は設けない。受け取り側はIDを検証し、ファイル名やパスへ無加工で転用しない。
- 同じ人物には同じ話者IDを使用する。**表示名が同じであっても、IDが異なれば別の話者**とみなす。表示名からIDを逆引きして同一人物と判断しない。
- `name` がなければ画面上は話者IDを表示できる。`kind` が不明な場合、地の文か登場人物かを名前だけから確定しない。
- 属性の列挙値は音声生成を助ける補助情報であり、値が不明なら省略してよい。

### 2.3 `segments`（台本項目）

| キー | 標準出力 | 意味 |
|---|---|---|
| `id` | 必須 | 台本項目の識別ID。作品内で重複しない |
| `speaker_id` | 発話では必須 | `speakers` の話者IDを参照。区切りでは省略可 |
| `text` | 発話では必須 | 原稿から切り出した原文。改変しない |
| `emotion` | 必須 | 発話の感情。読み込み時に省略されていたら `neutral` |
| `acting_description` | 任意 | その発話だけの演技指示 |
| `tts_text` | 任意 | 読みを調整した**発話全体**の読み上げ文。空文字列は有効な指定としない |
| `pause_after_ms` | 任意 | 発話・区切りの後の間。0以上の整数（ミリ秒） |
| `segment_type` | 任意 | `speech`（既定）または `separator`（読み上げない区切り） |
| `text_format` | 任意 | ルビ形式：`none` / `aozora` / `narou` / `kakuyomu` / `pixiv` |
| `blank_lines_after` | 任意 | この項目の直後の空行数。0以上の整数 |

- 発話IDは空でない文字列とし、標準出力では英数字・`_`・`-` を用いる。長さの固定上限は設けない。受け取り側はIDをファイル名やパスへ無加工で転用しない。
- `segments` の配列順が朗読順。受け取り側は自動的に並べ替えない。
- `segment_type: "speech"` では、`text` は空でない文字列を用いる。１発話に異なる話者の台詞を混在させない。未知の `segment_type` を `speech` と決めつけない。
- `segment_type: "separator"` は読み上げ対象外。原稿上の区切り行の文字を `text` に保存してよいが、`speaker_id` を持たなくてもよい。
- `text` は原文の保存先であり、読みの修正や表記の置換は `tts_text` にのみ行う。
- `tts_text` を指定するときは発話全体の読み上げ文とし、原文とは別に保存する。空文字列や空白のみの文字列は「未指定」と扱う。解釈に迷う語は無理に書き換えない。

発話全体の感情・話し方は emotion にIDを指定する。新しい候補と位置イベントの指示は 02_CHAT_PROMPT.md を参照する。以下の旧IDは引き続き読み込める。tired・giggleは旧形式の先頭付与として保持し、新規の位置指定にはtts_textを使う。

`neutral`（平静）/ `joy`（喜び）/ `anger`（怒り）/ `sad`（悲しみ）/ `kind`（優しさ）/ `tease`（からかい）/ `anxiety`（不安）/ `tension`（緊張）/ `surprise`（驚き）/ `tired`（疲れ・ため息）/ `whisper`（囁き）/ `giggle`（忍び笑い）/ `fear`（恐怖）/ `sleepy`（眠気）/ `resolve`（決意・強調）

追加IDとモデルへ渡す絵文字は次のとおり。

| ID | 絵文字 | ID | 絵文字 |
| --- | --- | --- | --- |
| panting | 🥵 | calling | 📢 |
| sleep_talking | 😴 | fast | ⏩ |
| telephone | 📞 | slow | 🐢 |
| pained | 😖 | worried | 😟 |
| shy | 🫣 | exasperated | 🙄 |
| cheerful | 😊 | confident | 😎 |
| pleading | 🙏 | drunken | 🥴 |
| humming | 🎵 | relieved | 😌 |
| questioning | 🤔 | strong | 💪 |
| narration | 📖 | | |

位置指定には `😮‍💨 ⏸️ 🤭 🌬️ 😮 💋 🥤 🤧 👌 👃` を `tts_text` の該当位置へ挿入する。Unicodeの結合文字・異体字セレクタを保持する。`⏸️` の無音時間は正確なミリ秒指定ではない。同じ絵文字の反復は強調の指定であり、非言語音の発生回数を保証しない。

`👅`（判別しにくい異音）、`🤐`（台詞に合わない声）、`🥱`（あくびの再現性不足・異音）、`😒`（反復時の異音）はAIの自動選択から除外する。手動入力・既存台本は保持する。効果不明瞭なタグは声との相性やCaptionで調整し、複合的な効果を持つタグも発話全体の感情・演技として指定できる。

短文の生成は15文字程度以上を目安にする。原文の水増しや異なる話者の結合は行わない。

## 3. 読みと間の解釈

### 3.1 読み上げる文字列の優先順位

1. 有効な `tts_text` があれば、その文字列を使う。
2. それ以外では、認識できる明示ルビを安全に変換できる場合に限って変換する。
3. 変換ができない場合は `text` を保持する。未変換ルビによって正しい読み上げが期待できない場合、生成前に警告または確認を求める。

`text_format` の発話別指定は、アプリの全体設定より優先する。指定がない場合のルビ形式は受け取り側が設定する。未知の `text_format` を推測で別形式に置き換えない。

### 3.2 発話後の間

- 有効な発話の `pause_after_ms` があればそれを優先する（`0` も明示指定）。
- 明示指定がなければ、区切りの `pause_after_ms`、区切りや `blank_lines_after` からの自動設定、アプリの共通設定の順に扱う。
- 自動設定の具体的なミリ秒値や、複数区切りの統合方法は、音声生成アプリ側が定める。原稿にない無音をJSONの `text` に付け足さない。

## 4. 読み込み時の許容と問題の扱い

標準出力に必要な項目が欠けていても、情報を失わず復旧できる場合は、受け取り側で編集用に読み込んでよい。次の表は、**受け取り側に求める基本動作**である。

| 入力の状態 | 読み込み時の動作 | 音声生成への影響 |
|---|---|---|
| 未知の追加キー | 既知の処理では無視する | 原則なし |
| 任意の文字列項目や人物属性が欠落・型違い・未知の列挙値 | 無視して未指定として扱う。必要に応じて警告 | 当該指定なしで進める |
| `emotion` の欠落・未知の値 | `neutral` として扱い、警告 | 原則なし |
| 不正な `pause_after_ms` / `blank_lines_after` | 無視してアプリの設定を使い、警告 | 既定の間を使用 |
| 空文字列・空白のみ・型違いの `tts_text` | 無視し、`text` を使う | 原文・安全なルビ変換を使用 |
| 未知の `text_format` | 読みを推測せず無視し、警告 | 未変換ルビがあれば確認 |
| 未知の `segment_type` | 元の値を保持して要確認にする。`speech` と決めつけない | 対象項目は生成不可 |
| `name` が欠落 | 話者IDを表示名として使い、警告 | 原則なし |
| `kind` が欠落・未知 | 種別未確定として保持し、警告 | 話者種別依存の処理は行わない |
| `id` が欠落・重複 | 元の項目を保持し、暫定ID付与などで編集可能にする。修復を通知 | 安定したIDが確定するまで生成不可 |
| `speaker_id` が欠落・未定義 | 原文と元の参照値を保持し、未割り当てとして表示 | 対象発話は生成不可 |
| `speech` の `text` が欠落・文字列でない・空 | 項目を保持してエラー表示。原文を推測補完しない | 対象発話は生成不可 |
| `speakers` / `segments` の欠落・型違い | 復旧可能な部分だけ保持し、構造エラーを表示 | 必要な構造を復旧するまで生成不可 |
| JSON構文が不正 / ルートがオブジェクトでない | 読み込みを中止し、エラーを表示 | 生成不可 |
| 明示された未知の `schema_version` | 対応形式か確認し、未対応なら中止。無条件にv1扱いしない | 未対応なら生成不可 |
| `schema_version` が欠落 | 構造がv1と判断できる場合に限り警告付きで取り込む | 他の条件を満たせば生成可能 |

- **警告**は、受け取り側で安全な代替処理ができる状態を指す。
- **要確認**は、読み込みはできるが情報の確定が必要な状態を指す。
- **エラー**は、読み込みや音声生成を安全に進められない状態を指す。
- 読み込み成功を、全発話の原文一致・話者同定・読みの正しさが保証された状態として表示してはならない。
- 要確認項目を黙って削除・スキップして全編を完成扱いにしない。部分生成を許す場合も、対象範囲と未生成項目を明示する。
- 未知の項目は利用に必須ではない。編集後に再保存するアプリが未知項目を保持できない場合、少なくとも元ファイルを上書きせず、未知項目が保存対象外であることを分かるようにする。

## 5. 原文の保全と検証

- `text` と `source` は、受け取った原文を保持するためのデータであり、取り込みや再保存の都合で自動的に言い換えたり句読点・空白を補ったりしない。
- `source` は任意であり、シナリオJSONに存在しても、その内容が正しい原稿だと独立に保証されるわけではない。信頼できる元の原稿が別にある場合、照合に用いる。
- `source` と `segments` の照合には、区切り・空行・改行などの扱いが関係する。単純な文字列連結が一致しないという理由だけで原稿を修正してはならない。
- 照合ができない場合は「原文照合未実施」と表示する。欠落・重複が確認された場合は該当箇所を示し、人間またはLLMとの対話で修正する。
- ハッシュなどの機械的な整合性確認は受け取り側が行う。シナリオ生成LLMにハッシュの算出を要求しない。`source_sha256` はv1の標準フィールドではない。

## 6. 作品規模と実行環境

- この形式は話者数・発話数・原稿文字数・各発話の文字数・JSON総容量について、固定の上限を定義しない。
- 各アプリは、メモリ容量、表示性能、音声合成エンジンの入力長、実行時間などに応じた上限を設けられる。
- 実行環境上の上限に達した場合、シナリオ全体を不正とみなさず、その環境で扱えない理由を示す。章・場面ごとの読み込み、ページ分割、逐次処理などを選択できることが望ましい。
- 上限に合わせて原文を黙って切り詰めたり、発話を削除したりしてはならない。
- TTSの1リクエスト当たりの長さと、シナリオJSONの1発話の長さは別の概念である。必要な場合、合成時に発話を内部的に分割する。

## 7. 互換性・出力・用語

- 正規のシナリオ形式は `schema_version: 1` と `speakers` / `segments` を持つJSONとする。
- CLI固有のプロジェクト形式など別形式は、読み込みアダプターで変換してよい。**別形式のキーをこの標準形式に混在させない。**
- v1の既存フィールドの意味は変更しない。意味を変える改訂が必要なら形式バージョンの更新を検討する。
- 標準形式で再保存する際は、ID・項目順・原文・読み上げ文・有効な付加情報を保持する。変換で失われる情報がある場合は、少なくとも黙って上書きしない。

画面・説明文・LLM用依頼文で用いる日本語は、次に統一する。

| JSON内部キー・技術用語 | 表示する日本語 |
|---|---|
| `source` | 原稿全文 |
| `speakers` / `speaker_id` | 話者一覧 / 話者ID |
| `segments` / segment | 台本項目 / 発話（読み上げる項目） |
| `text` | 原文 |
| `tts_text` | 読み上げ文 |
| `bio` | 人物像 |
| `voice_caption` | 声の特徴 |
| 話者の `acting_description` | 普段の話し方 |
| 発話の `acting_description` | 発話ごとの演技指示 |
| `emotion` | 感情 |
| `pause_after_ms` | 発話後の間 |
| `segment_type: "separator"` | 区切り（読み上げない） |
| 参照WAV | 参照音声 |

## 8. LLM用依頼文との役割分担

- この文書はJSONの契約を定める。質問の仕方、読みの相談、長編の分割、人物メモの管理方法は別文書で定める。
- LLMには、原稿を読みながら人物一覧と未確定事項を更新し、判断に迷う箇所だけ相談する運用を許す。全原稿の再読、機械的な検証、数値上限への調整を無理に要求しない。
- 長編を分割する場合、分割単位ごとの発話IDを重複させず、同一人物の話者IDを一貫させる。未確定情報を無理に断定しない。
- JSONを書き出しただけで「原文照合済み」「試聴済み」と申告しない。検証・修正・試聴は受け取り側と利用者の工程とする。


## Koebuta v1.00 編集用の任意拡張

発話の `koebuta_edit` は編集履歴を示す任意オブジェクトです。標準JSONの必須項目は変更しません。

```json
{"koebuta_edit":{"actions":["split"],"needs_review":true,"fallback":false}}
```

`actions` は `split`（自動分割）、`merge`（自動結合）、`manual_split`、`manual_merge` の履歴です。`needs_review` は利用者による確認待ち、`fallback` は自然な区切り候補がなく文字数付近で分割した印です。音声生成の内容・感情指定には使用しません。未知項目を扱えない外部ツール向けには除去可能です。Koebutaでは未知の任意キーと同様に往復保持します。
